## 3. 症状：准确描述 + 我的两次判断错误（这部分最值钱）

### 3.1 现在的症状

`G:\_ds\now_1.jpeg`（2026-10-24，第 29 天，白天，合作者的 105 库）：
**整个地表是一层品红/绿/青的"等高线状"噪声场**，斑块边界跟着地形特征走（小路、草地的形状仍读得出来），

`G:\_ds\ao_fair_5.jpeg`（第 2 天，黄昏，同一版）：同样的噪声**只出现在部分地块**，门和 HUD 干净。
`G:\_ds\ao_fair_3.jpeg`（第 1 天，夜里）：地面看起来"正常"——**因为暗，噪声被藏住了**。

### 3.2 我犯过的两个错，别再犯

**错误一：进世界 30 秒拍一张，看到黑，就判"合作者的库世界全黑、非 drop-in"，并因此换回我们自己的库。**
真相：饥荒新世界开场就是夜里，前 1–2 分钟本来就黑。这条误判直接导致我们多花了一整轮，
并且**差点让我们把别人正确的修复当成坏的丢掉**。
⇒ 规矩：**`@draws` ≥ 700 才算进世界；进世界后等 ≥150 秒；走动一次；拿同一物体和基线并排比。**
⇒ 截图字节数当粗代理：全黑 ~123–127 KB，有内容 ~296–304 KB，满屏噪声 ~488–550 KB。

**错误二：只比了夜里的门，就宣布"门的彩点在他的库下不存在、是我们 Z3 库带的缺陷"。**
这一条**可能仍然成立**（两张图都是夜里、同一物体、同一 .so：`ao_walk2_1.jpeg` 满是绿碎片 vs `ao_fair_3.jpeg` 干净），
但**白天地表这一族我从来没做过两套库的对照**，所以"谁的库更好"这个问题**没有答案**。
⇒ 下一个人的第一件事见 §6 的实验 A。

### 3.3 已经确认不是"黑屏"，是"花屏"

他（机主）的原话：「现在进去世界就是花屏 不再是黑色再转花屏」。
意思是：以前是"先黑一阵再花"，现在是"一进去就花"。原因很可能是那一阵黑**本来就是夜里**，
而这次载入时世界已经是白天 ⇒ 没有暗场遮着了。**"黑"从来不是渲染故障，"花"才是。**

## 4. 构建 → 打包 → 装机 → 驱动（可复现的四步）

1. **构建 .so**：`bash G:\qoder/tmp/ds_AObuild.sh`
   把 `git diff --name-only $BASE HEAD` 里 `dm/**.(c|h)` 的文件 tar 到构建机 `~/ds-absorb`，重链，
   **三道门槛**：①未定义 `_Z` 符号数 = 0；②剩余未定义符号必须全是 WEAK；③新加的字符串真的在二进制里。
   scp 回来后**必须 `cp` 到 `/g/_ds/`**（Git Bash 的 `/tmp` 其实是 WSL 侧的 `/mnt/c/...`，会拿错文件）。
2. **打包 HAP**：`bash G:\qoder/tmp/ds_packAO.sh`（只换 .so）或 `ds_packAOL.sh`（同时换 `shaders.bin`，
   参数 `SHBSRC` / `SHBMD5`）。内部是无头 `hvigorw … assembleHap --no-daemon`，PATH 里要有 JDK 的 bin。
   **包内自审**：hvigor 会剥符号，所以"包内 .so md5 == 源 md5"是**无效断言**；
   正确做法是断言标记字符串在包里 + 断言包内比源小。`shaders.bin` 是 resfile，不剥，**可以逐字节 md5 断言**。
3. **装机**：`MKMODE=none bash G:\qoder/tmp/ds_hapgo.sh <TAG>`
   大包**不能用 `hdc install -r`**（会截断并假报 verify signature failed）；
   必须 `hdc file send` 到 `/data/local/tmp` 再 `bm install -r -p <路径>`。
4. **带参数启动**：`bash G:\qoder/tmp/ds_relaunch.sh <TAG>`，读 `G:\_ds\params_<TAG>`。
   **参数必须在 `aa start --ps` 里给**，桌面图标点进去等于所有判别开关全关。
   设备锁屏时 `aa start` 直接报 `Error Code:10106102`（开发者模式不会自动解锁），得人手解锁。
   脚本每轮会重压 `power-shell timeout -o 2147483647`（永不息屏）。

**驱动到世界的按键序列**（`ds_padtap.sh <键>`，坐标来自 `entry/src/main/ets/model/PadLayout.ets`）：
主菜单 → `ddown` → `a`（世界列表）→ `a`（第一行存档）→ 世界设置面板 → **`plus`（=启动服务器，别按 a，焦点在"名称"上会弹软键盘）**
→ 等 2–5 分钟（`@draws` 卡在 134 且省略号在走 = 正在生成/起服务器）→ `@draws` 跳到 620–650 = 选角页
→ `a`（进衣柜）→ `dup`（把焦点从皮肤格移开）→ **`plus`（出发!）** → `@draws` ≥ 700 = 在世界里。
走动：`uitest uiInput swipe 239 545 380 480 900`（左摇杆往右上推），重复若干次。

**判"跑到哪了"不看截图，看 `@draws`**：`bash ds_scene.sh nvn_<TAG>.tsv 6`。
指纹：2 启动 · 12–14 开场/标题 · 40–44 子菜单 · 84–137 世界设置弹窗 · 15 载入 · 620–651 选角 · **700+ 真实世界**。

## 5. 已经用证据排除/证死的（别回头再查）

以下每一条都有真机计数或离线产物支撑，不是推测：

- **着色器覆盖不是问题**：整轮 `无库0 跳过0 无管线0`，`缺键` 一行都没有。105 条库对这个世界是够的。
- **管线/编译不是问题**：`建败0 管线败0（组内0 组外0）`。
- **描述符/绑定表错配不是问题**：离线把两套库的世界段 SPIR-V 抽出来对比（`G:\_ds\libcmp\`），
  **接口完全一致**（同输入输出、同两个 `sampler2D` 绑在 binding 1/2）。
- **BC 软解不是可用的替代路径**：`DM_RT_ASTC 0`（回退到 BC→RGBA8 软解）后世界**整层全黑**，
  `当场败53 环拒12 BC层2449`。⇒ 世界能看见**全靠设备端 BC3→ASTC 现编**，软解只能当诊断旁路。
- **color write mask 不是问题**：`色掩或15与15`（布尔，不是位掩码）。
- **"世界层红通道恒为 0"这条已结案**：那是**夜里截图的读数**。白天/过场原画里红围巾、格子衫、
  羊皮纸底色、HUD 红心全对（`ao_fair_6.jpeg`、`ao_fair_7.jpeg`）。
- **"多部件几何撕裂"（旧 §0）在菜单/标题层已修**：`title_before_an.jpg` → `title_after_an.jpg`。
- **哑图这一轮是 0**：`哑0`（历史上有过 `哑3067`、`当场顶139` 那批，都定性成 RT 链，不是丢贴图）。
- **`s=924` 那张 640×360 是假把手**：菜单页和世界内**恒为纯黑、校验和 `8f6771d5` 一次不变**，
  是饥荒自己的全屏黑遮罩，不是丢失的实体层。
- **上游 seedds/nxnative 的 `cb_extent.tsv` / `shader_facts.tsv` 对本项目不适用**（Metal 专属 / 需要 PC 版着色器配对）。
- **`DM_SAMPLE 0` 不是关闭**：单位是毫秒，`0` 会起一条 0 微秒周期的线程，8 分钟打 2 GB 日志。
  `dm/host/diag.c` 已加 `if (ms <= 0) return;`。

### 实验 C —— 把噪斑那张图的真内容拿到手

`DM_TEXDUMP=<沙箱内绝对目录> DM_TEXDUMP_MIN=<serial下限> DM_TEXDUMP_MAX=<上限>`，

## 7. 花屏的候选机制（按我的判断排序，但都还没被证）

**共同观察**：噪声是**低频、blobby、跟着地形特征**的，不是 4×4 块状网格、也不是斜纹或整行位移。
⇒ 这个形状**不像**块排布/行距错（那会出网格或斜纹），**更像**"采样了一张内容根本不对的图"。

- **H1（我最怀疑）：地表被乘了一张我们从未写入/从未 flush 的图**（光照图、遮蔽图或 tint 图）。
  夜里那张恰好是黑的 ⇒ 乘出来是暗，看着"正常"；白天它是垃圾内存 ⇒ 满屏噪声。
  这条能同时解释"夜里干净、白天花"和"HUD/文字干净（它们不乘这张图）"。
  判别 = 实验 B 的 `t*.*=空` + 实验 C 的读回。
- **H2：`rt_bc3_to_astc`（设备端 BC3→ASTC 现编）对某些规格源几何错**（mip 级数、层、GOB 填充）。
  历史上衣柜页的"百叶窗撕裂"就定性到这一族。判别 = 实验 C，看噪斑那张是不是落在特定规格档（如 1024×512 / 11 级 mip）。
- **H3：cls-0（BC1/BC4，8 字节块）没被覆盖**。整轮唯一非零的贴图侧异常是 `打包:… BC层130`
  （其余 `卡环0 越界0 解排0 格式0 深度0 三维0 环拒0` 全是 0）。任务 #15 一直没做。
  判别 = 数噪斑区域贴图的**块字节数**（8 还是 16）。
- **H4：附件级/层被丢**（任务 #53 未完成）：`do_set_rt` 忽略客体的 `cview/has_cview/dview/has_dview`，
  永远取 level 0 / layer 0。若地表用的是带 mip 或数组的附件，会读到错的那一层。

**注意**：以上四条**互不排斥**，而且我一条都没证死。别按我排序直接动手。

## 8. 仪器陷阱（每一条都烧掉过一轮）

1. **帧率只能用 tsv 的"末帧"差值算**。`ds_driveAO.sh fps` 那个动作会报 `0.0 FPS`（两次读的计数器没变），
   而同一时刻 tsv 帧号在涨。机主实测 12.5 FPS 时它报 0.0。
2. **`snapshot_display -f` 不覆盖同名文件**。反复用同一个设备路径截图，`file recv` 拿回来的是**同一份旧图**（md5 一模一样），
   会误判"画面卡住"。**每拍一张换一个文件名。**
3. **`snapshot_display` 只认 `/data/local/tmp/*.jpeg`**，然后 `hdc file recv` 的目标要写 **Windows 风格路径**（`'G:\_ds\x.jpeg'`）。
4. **`%{public}` 只能出现在 `OH_LOG_Print` 的格式串里**；塞进 `snprintf` 的目标串会把日志打花。
5. **`[vk]` 前缀的日志进 `DM_LOGFILE`，`[dm]` 前缀的只进 hilog**。取错地方会以为"什么都没打"。
6. **设备上有 `hilog`，没有 awk/python**。所有解析拉回 PC 做。
7. **多 GB 的 hilog 别用 grep/tail**（超时）。用分块流式检索（`/tmp/findsrc.js`，64 MB 窗口）。
8. **Node 里别写 Git-Bash 路径**：`/g/_ds` 会被解析成 `C:\g\_ds`。写 `G:/_ds/...` 或 `cygpath -w` 转。
9. **本机没有 `python3`/`gcc`**；数 CR 用 `tr -dc '\r' | wc -c`（`wc -l` 恒 0）。
10. **仓库行尾是逐文件的**：`dm/gfx/nvn/nvn_vulkan.c` 和 `dm/ohos/app_ohos.c` 是 **CRLF**，其余是 LF，
    `core.autocrlf=false`、无 `.gitattributes`。工具重写会造整文件假 diff。
    核对：`git cat-file blob HEAD:<f> | tr -dc '\r' | wc -c`。
11. **"计数为 0"只证明"我采样的那个范围内没走到那条分支"**，不证明数据完整。
